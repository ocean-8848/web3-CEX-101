## 场景 3：下单调用链

**画面标题**：一笔下单，穿过六个服务（逐步动画）

**[3.0]** 场景是这样的。用户 A 用 USDT 买 0.1 个 BTC，限价 60,000，这是示例。请求先打到 API 网关。

**[3.1]** 网关先校验 session 或 API Key 签名，再做限流。它还要检查幂等键，防止同一个请求被提交两次。

**[3.2]** 网关把请求交给订单服务。订单服务先问风控：精度对不对，价格偏离大不大，余额够不够。风控回复通过。

**[3.3]** 接着，订单服务让账本冻结 6,000 USDT。也就是 0.1 乘以 60,000。

**[3.4]** 冻结成功，订单才提交给撮合引擎。撮合按价格优先、时间优先配对，返回成交回报：成交 0.1 个 BTC。

**[3.5]** 订单服务再调用结算。结算服务让账本扣掉冻结的 USDT，写一条记账分录，拿回分录编号。

**[3.6]** 最后，订单状态变成已成交，网关给用户返回 200 OK。到这里，一共十几个同步步骤。用户等待的，就是这整条同步链。任何一步失败，请求就失败。

## 场景 4：钱什么时候扣掉

**画面标题**：只盯着账本里的数字看（逐步动画）

**[4.0]** 现在只盯着账本里的数字。下单前，用户 A 有 10,000 USDT 可用，这是示例数字。

**[4.1]** 冻结那一步，6,000 USDT 从可用转到冻结。可用剩 4,000，总额还是 10,000。钱还没离开 A。

**[4.2]** 结算那一步，冻结的 6,000 被扣掉，A 拿到 0.1 个 BTC。这时，钱才真正换了手。手续费我们留到第 11 集再讲。

**[4.3]** 再看对手方。卖家 B 冻结的 0.1 个 BTC 被扣掉，拿到 6,000 USDT。两边加起来，USDT 和 BTC 的总量都没变。

**[4.4]** 所以开头的问题有了答案。钱在下单时被冻结，在结算时才真正扣掉。冻结，是一个中间状态。故障最容易出现在这里，我们稍后细看。

## 场景 5：响应之后的异步事件

**画面标题**：200 OK 之后，事件才开始流动（逐步动画）

**[5.0]** 用户拿到 200 OK，事情还没完。账本发出一条记账完成事件，订单服务发出一条成交事件。它们都进入 Kafka。

**[5.1]** 行情服务从 Kafka 消费成交事件。再通过 WebSocket，把盘口和成交推给所有用户。私有的余额变化，也走同样的路，推给用户自己。

**[5.2]** 注意这里的区别。前面的实线是同步调用，直接决定请求的成败。这里的虚线是异步事件。

**[5.3]** 行情推送慢几百毫秒，不影响任何人的资金正确性。所以它放在异步区，不拖慢下单。

**[5.4]** 补充一点。小型系统可以让订单服务同步调用结算。大型交易所的业界做法，是撮合把成交写进日志流，结算服务异步消费。

## 场景 6：充值调用链

**画面标题**：充值：由链上事件触发（逐步动画）

**[6.0]** 再看充值。用户先通过网关，向钱包服务申请一个 ETH 充值地址，拿到一个专属地址。

**[6.1]** 用户从自己的钱包，向这个地址转 1 个 ETH。注意，这一步发生在链上，交易所还不知道。它只能等索引器在区块里发现这笔转账。

**[6.2]** 索引器每出一个新区块就扫描一次，匹配充值地址。发现这笔转账时，确认数是 1，状态是待确认。

**[6.3]** 区块继续往上长。确认数 1、2、3，一直数下去。没到阈值之前，用户的余额不变。

**[6.4]** 确认数达到阈值，示例是 12。钱包服务调用账本记账，用户的 ETH 加 1。再通过 Kafka，推送充值到账。

**[6.5]** 为什么要等确认数？为了防止链重组。如果入账以后区块被回滚，用户的币到了账，链上的钱却没了。

**[6.6]** 还有一条铁律：入账必须幂等。同一个交易哈希被扫描两次，只能入账一次。整条充值链，都是异步的。

## 场景 7：提币调用链

**画面标题**：提币：先冻结，后出账（逐步动画）

**[7.0]** 再看提币。用户要把 0.5 个 ETH 提到外部地址。钱包服务先找身份服务，校验 2FA 和用户状态。

**[7.1]** 然后检查白名单、限额和风控规则。都通过了，让账本冻结 0.5 个 ETH，状态变成已申请。

**[7.2]** 接着是审核，可以人工，也可以自动。大额提币，通常要由运营后台人工审核。审核通过，钱包服务让托管适配器创建转账。

**[7.3]** 托管适配器签名并广播，拿到交易哈希。注意，私钥在托管层，钱包服务碰不到私钥。

**[7.4]** 索引器看到这笔交易的确认数达到阈值，钱包才让账本出账。冻结的 0.5 个 ETH，正式扣掉。提币到这里，才算真正完成。

**[7.5]** 如果审核拒绝呢？系统执行的是解冻，而不是出账。0.5 个 ETH 回到可用余额。

## 场景 8：同步与异步的边界

**画面标题**：这一步失败时，用户的请求该不该失败？

**[8.0]** 把三条链放在一起，就能画出同步和异步的边界。左边是同步区，这些步骤直接影响用户请求的成败。比如风控拒绝了，订单就不能下成功。

> 画面：同步区：决定请求成败 网关 → 订单订单 → 风控订单 → 账本冻结订单 → 撮合钱包 → 2FA 校验

**[8.1]** 右边是异步区，走 Kafka 事件，最终一致。行情、余额推送、充值确认、提币状态回查、对账报表，都在这里。

> 画面：异步区：Kafka 事件，最终一致 成交 → 行情推送账本 → 私有 WS 余额推送链上 → 充值确认托管 → 提币状态回查账本 → 对账和…

**[8.2]** 判断标准只有一句话。这一步失败时，用户的请求是否应该失败？是，就放同步区。否，就放异步区。

> 画面：该失败 → 同步区；不该失败 → 异步区

**[8.3]** 同步区越长，下单延迟越高，故障面也越大。异步区的代价是延迟。Kafka 堆积时，用户会看到已成交、余额没变。

> 画面：同步越长，延迟越高；异步的代价是延迟

**[8.4]** 异步事件处理失败会重试。超过重试次数，就进入死信队列，等待人工处理。

> 画面：失败重试，超限进入死信队列 dead-letter

## 场景 9：Outbox 模式

**画面标题**：记账和发事件，怎样不会一个成功一个失败？（逐步动画）

**[9.0]** 这里有个细节。账本记完账，要发一条事件。记账和发事件涉及两个系统，怎么保证不会一个成功、一个失败？

**[9.1]** 先看错误的做法。先写数据库，再发 Kafka。如果写完库，进程正好崩溃，事件就丢了。账变了，下游没人知道。

**[9.2]** 反过来，先发事件再写库，也不行。事件发出去了，库却没写成。下游看到的，是一笔不存在的账。

**[9.3]** 正确做法叫 Outbox 模式。服务把记账分录和一条待发事件，写进自己数据库的同一个事务。要么都成功，要么都失败。

**[9.4]** 后台任务再从 outbox 表里读出事件，发到 Kafka。发送失败就重试。所以下游通常要按事件编号去重。常见的组合，就是 PostgreSQL 加 Kafka outbox。

## 场景 10：最危险的一步

**画面标题**：冻结之后、撮合之前，撮合引擎宕机了（逐步动画）

**[10.0]** 现在来看故障。整条下单链路里，最危险的一步是冻结成功之后、撮合之前。

**[10.1]** 假设这时撮合引擎宕机。6,000 USDT 已经冻结，订单却没进订单簿。用户看到的是下单失败。

**[10.2]** 系统要补偿。订单服务把订单标记为已拒绝，再调用账本解冻。6,000 USDT 回到可用，余额恢复原样。

**[10.3]** 注意，补偿动作必须幂等。假设解冻请求超时，订单服务又重试了一次，解冻执行了两次。

**[10.4]** 如果没有幂等保护，可用余额会变成 16,000。用户凭空多出 6,000 USDT。这是真实的资金损失。

**[10.5]** 所以每次解冻都带一个唯一的请求编号。账本看到重复的编号，直接返回第一次的结果，不再改余额。

## 场景 11：更多故障

**画面标题**：用户看到什么，系统怎样补偿

**[11.0]** 第二种故障，Kafka 堆积。用户看到订单已成交，但余额和推送都延迟。账本其实已经正确，只是事件慢了。消费者追上，就自动恢复。

> 画面：Kafka 堆积看到：已成交，余额和推送延迟补偿：账本已正确，消费者追上即恢复

**[11.1]** 第三种，结算失败。用户看到订单成交了，资产却没变。系统会重试结算。多次失败后进入死信，由运营后台人工处理。

> 画面：结算失败看到：订单成交，资产没变补偿：重试，多次失败进死信，人工处理

**[11.2]** 第四种，索引器落后，充值迟迟不到账。索引器追上区块后补齐入账。因为按交易哈希幂等，不会重复入账。

> 画面：索引器落后看到：充值迟迟不到账补偿：追块补入账，按交易哈希幂等

**[11.3]** 第五种最隐蔽。提币广播成功，但索引器宕机。提币停在已广播状态。币已经离开热钱包，账本却还没出账。这要靠对账任务发现。

> 画面：广播成功，索引器宕机看到：提币停在已广播补偿：币已离开热钱包，靠对账发现

**[11.4]** 这些故障，都能在交互实验 architecture-explorer 里注入。看看每个场景在哪一步失败，系统又怎样补偿。

> 画面：动手试试：architecture-explorer 里在节点上注入故障，看每个场景在哪一步失败。

## 场景 12：小结与预告

**画面标题**：记住三件事

**[12.0]** 小结一下。第一，下单是一条同步链：网关、订单、风控、账本冻结、撮合、结算。钱在冻结时锁住，在结算时才真正扣掉。

> 画面：下单是同步链：钱在冻结时锁住，在结算时才扣掉。 ｜ 充值等确认数再入账；提币先冻结、后出账，拒绝就解冻。

**[12.1]** 第二，充值和提币由链上事件驱动。充值要等确认数再入账。提币先冻结、后出账，被拒绝就解冻。

**[12.2]** 第三，同步区决定成败，异步区追求最终一致。Outbox 保证记账和发事件一起成功，所有补偿都必须幂等。

> 画面：同步定成败，异步求最终一致；Outbox 防丢事件，补偿必须幂等。

**[12.3]** 下一集，我们回到调用链的第一站：账户与身份。登录、2FA、API 签名和 KYC，交易所怎样确认你就是你。我们下集见。

> 画面：下集 EP04账户与身份：登录、2FA、API 签名、KYC
