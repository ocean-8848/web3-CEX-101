## 场景 3：多机房与灾备

**画面标题**：状态不同，高可用策略也不同（逐步动画）

**[3.0]** 先看高可用。这是一个双机房的布局。用户先到全局流量调度，再分到两个机房。

**[3.1]** API 网关没有本地状态，可以多活。两个机房都接流量，用负载均衡分流。

**[3.2]** 撮合引擎不同。订单簿在内存里，必须严格有序。所以是单主加热备，按交易对分片。热备消费同一份有序事件流，订单簿和主节点保持一致。

**[3.3]** 账本存的是资金余额，要强一致。主库同步复制到另一个机房。业界常见的取舍是，撮合同机房求低延迟，账本跨机房求强一致。

**[3.4]** 现在机房 A 故障。流量调度把用户切到机房 B，撮合热备接管成为新主，账本从库提升为主库。

**[3.5]** 最危险的情况是脑裂。主备同时认为自己是主，两个撮合引擎同时成交，就会重复成交。

**[3.6]** 所以要用租约或仲裁服务，保证同一时刻只有一个主。这是客机比喻不准的地方。两个机房可能互相看不见，必须靠第三方来裁决。

## 场景 4：主备切换与冷启动重放

**画面标题**：快照 + 有序指令日志 = 可重建的订单簿（逐步动画）

**[4.0]** 撮合引擎把订单簿放在内存里。进程一退出，内存就没了。所以必须能从持久化数据重建。

**[4.1]** 重建靠两样东西。快照，是某一时刻订单簿的完整副本。指令日志，是快照之后的全部指令，按序号严格排序。

**[4.2]** 正常时，主节点不断写入指令，热备一直跟着回放。举个示例，主节点写到1005，热备回放到1003。

**[4.3]** 这时主节点心跳超时。仲裁服务确认它失联，撤销它的租约，再把租约授予热备。

**[4.4]** 热备先把日志补齐到1005，再校验订单簿哈希。然后宣布成为主节点，从1006开始接收。

**[4.5]** 订单服务会重发没收到确认的指令。新主按序号去重，1004和1005直接跳过。没有序号，同一笔订单就可能成交两次。

**[4.6]** 没有热备时，就是冷启动。加载最近的快照，再回放之后的全部日志。日志越长越慢，所以要定期生成快照。

## 场景 5：降级与恢复顺序

**画面标题**：按影响范围逐级降，恢复时反向开（逐步动画）

**[5.0]** 部分故障时，系统要主动降级。关掉非核心功能，保护核心功能。

**[5.1]** 降级按影响范围从小到大排。第一级是限流，降低 API 配额。

**[5.2]** 第二级是暂停充提。触发条件是链节点异常，或者对账不平。

**[5.3]** 第三级是只读模式，禁止下单，触发条件是撮合或账本异常。需要停机修复时，才进入全站维护。

**[5.4]** 恢复顺序反过来。先开放查询，再开放撤单，然后开放下单，最后恢复充提。这样用户先看到真实余额。

> 画面：恢复顺序查询→撤单→下单→充提

**[5.5]** 注意两个坑。只读期间，行情服务不能继续推送旧价格。暂停充提期间，链上充值照样会到，恢复后必须补扫这段区块。

> 画面：只读期间：行情不能继续推旧价格 暂停充提期间：链上充值照样到，恢复后补扫区块

## 场景 6：可观测性

**画面标题**：最重要的告警：资金对不上

**[6.0]** 第二段，怎样尽早发现问题。可观测性，就是通过系统输出的信号，判断系统内部的状态。信号有四类。

> 画面：指标现在怎么样？下单延迟 P99、提币队列长度 ｜ 日志发生了什么？订单状态变化、后台审计日志

**[6.1]** 指标回答现在怎么样，比如下单延迟 P99。日志回答发生了什么，比如每次后台操作的审计记录。

**[6.2]** 链路追踪回答慢在哪里。一笔订单从网关到结算，每一段耗时都看得到。告警回答谁需要立即处理。

> 画面：链路追踪慢在哪里？网关→风控→冻结→撮合→结算 ｜ 告警谁要立即处理？账本不平、热钱包余额异常下降

**[6.3]** 注意，交易所最重要的告警不是服务挂了，而是资金对不上。服务挂了，用户马上发现。资金对不上，可能几天后才有人发现。

> 画面：服务挂了，用户马上发现。资金对不上，可能几天后才有人发现。

**[6.4]** 所以告警要分级。P1 是资金错误和账实不一致，立即呼叫值班。P2 是核心交易受影响，示例15分钟内响应。P3 在工作时间处理。

> 画面：P1 资金错误、账实不一致 · 立即呼叫 P2 核心交易受影响 · 示例 15 分钟 P3 非核心异常 · 工作时间

## 场景 7：安全纵深四层防线

**画面标题**：攻击者必须突破所有层，才能造成损失

**[7.0]** 第三段，怎样不被攻破。安全纵深，就是设多层独立防线。攻击者必须全部突破，才能碰到用户资产。

> 画面：攻击者→ ｜ 用户资产

**[7.1]** 第一层是网络层，让攻击者进不来。比如 DDoS 防护、WAF，核心服务不暴露在公网。

> 画面：网络层进不来DDoS 防护、WAF、核心服务不暴露公网

**[7.2]** 第二层是账户层，让盗号者拿不走。2FA、设备绑定、提币白名单，新地址提币还要延迟。

> 画面：账户层拿不走2FA、设备绑定、提币白名单、新地址延迟

**[7.3]** 第三层是密钥层，让黑客和内鬼签不了名。冷热钱包分离，MPC 或多签，加上硬件安全模块。热钱包只放日常提币需要的一小部分资产。

> 画面：密钥层签不了冷热分离、热钱包限额、MPC 或多签、HSM

**[7.4]** 第四层是内控层，让单人做不成恶。高风险操作一人发起、一人审批，这叫四眼原则。权限要最小化，客服能查信息，不能改余额。

> 画面：内控层单人做不成恶四眼原则、权限最小化、操作审计

**[7.5]** 最后一条底线。任何人，包括管理员，都不能绕过账本直接改余额。否则审计和对账就失去了意义。

> 画面：底线：任何人，包括管理员，都不能绕过账本直接改余额。

## 场景 8：案例一：2019 币安热钱包被盗

**画面标题**：币安热钱包被盗约 7,000 BTC（逐步动画）

**[8.0]** 第四段，复盘真实案例。以下数据均据公开报道，金额按事发时市值估算。第一个，2019年币安热钱包被盗。

**[8.1]** 根因在用户侧。攻击者通过钓鱼、病毒等手段，收集了大量用户的 API 密钥和 2FA 验证码。

**[8.2]** 攻击者长期潜伏，等待时机。风控规则没有识别出多个账户在短时间内协同提币。

**[8.3]** 2019年5月7日，攻击者在一笔交易里提走约7000个 BTC。按当时市值，约4000万美元。

**[8.4]** 币安暂停充提约一周，并用 SAFU 基金全额覆盖损失，用户没有承担损失。

**[8.5]** 复盘一下。被突破的是账户层和风控层，密钥层没有被突破。热钱包限额起了作用，损失只占 BTC 总持仓的约2%。

**[8.6]** 改进是加强 API 提币风控、行为分析和提币审核。SAFU 这样的储备，也成了用户信任的一部分。

## 场景 9：案例二：2022 BNB Chain 跨链桥

**画面标题**：BNB Chain 跨链桥：凭空铸造 200 万枚 BNB（逐步动画）

**[9.0]** 第二个案例，2022年10月6日，BNB Chain 的跨链桥漏洞。

**[9.1]** 根因是 BSC Token Hub 跨链桥的证明验证存在漏洞。攻击者伪造了跨链证明。

**[9.2]** 结果是凭空铸造了200万枚 BNB，当时约5.7亿美元。

**[9.3]** 攻击者把部分资产跨链转出。最终实际转出的损失，估计约1亿到1.1亿美元。

**[9.4]** BNB Chain 协调验证者暂停了链的运行，并冻结攻击者地址，部分资产被冻结。

**[9.5]** 注意，这是链层事故，不是交易所账本事故。交易所用户的账户余额没有被直接修改。

**[9.6]** 暂停整条链，也引发了关于去中心化程度的讨论。对交易所的启示是，异常大额充值和刚升级的链，要加确认数和人工审核。

## 场景 10：案例三：2022 FTX

**画面标题**：FTX：不是黑客，是内控和治理失败（逐步动画）

**[10.0]** 第三个案例，2022年的 FTX。以下据公开报道和美国法院文件。这不是黑客事故，而是内控和治理失败。

**[10.1]** 根因是客户资产和关联公司资金混用。账本里存在特殊权限账户，可以无限透支。

**[10.2]** 储备也不透明，外部无法验证。2022年11月初，媒体披露了关联公司 Alameda 的资产负债表。它大量依赖 FTX 自己发行的 FTT 代币。

**[10.3]** 用户开始集中提币。FTX 无法兑付，于11月11日申请破产保护。

**[10.4]** 调查显示，FTX 把客户资产转给 Alameda 使用，形成约80亿美元的缺口。

**[10.5]** 2023年11月，陪审团判定创始人 Bankman-Fried 欺诈等罪名成立。2024年3月，他被判处25年监禁。

**[10.6]** 这次事件引发了行业信任危机。改进方向是储备金证明、客户资产隔离，以及监管要求的托管分离。

## 场景 11：案例四：2014 Mt.Gox

**画面标题**：Mt.Gox：账和实脱节，多年无人发现（逐步动画）

**[11.0]** 第四个案例，最早也最经典，2014年的 Mt.Gox。它曾是全球最大的比特币交易所。

**[11.1]** 根因是没有定期的账实对账。热钱包被长期持续盗取，账本余额和链上余额长期不符，多年没人发现。

**[11.2]** 2014年2月，Mt.Gox 暂停提币，随后申请破产。约85万枚 BTC 下落不明，当时约4.5亿美元。之后找回约20万枚。

**[11.3]** Mt.Gox 当时归因于交易延展性漏洞。部分细节在公开报道中说法不一。

**[11.4]** 2018年，破产程序转为民事再生程序，债权人因此可以按 BTC 获得赔付。2024年7月起，受托人开始大规模返还，距离倒闭已有10年。

**[11.5]** 核心问题是账和实脱节。如果每天对一次链上余额和账本余额，第一天就能发现异常。这也是定期对账制度的直接来源之一。

## 场景 12：四个案例对比

**画面标题**：用户最后会不会买单？

**[12.0]** 把四个案例放在一起比。

**[12.1]** 2019年币安被盗，突破的是账户层和风控层。SAFU 覆盖，用户没有承担损失。

> 画面：2019 币安被盗账户层、风控层否 · SAFU 覆盖热钱包限额 + 储备基金

**[12.2]** 2022年跨链桥，突破的是链协议层，用户余额没变。教训是跨链组件要有限额和紧急开关。

> 画面：2022 BNB 跨链桥链协议层否 · 余额未变跨链组件限额 + 紧急开关

**[12.3]** FTX 突破的是内控层和治理层，损失由用户承担，走破产程序。教训是客户资产隔离加储备金证明。

> 画面：2022 FTX内控层、治理层是 · 破产程序客户资产隔离 + 储备金证明

**[12.4]** Mt.Gox 突破的是密钥层和对账，用户多年后才拿到部分赔付。教训是每日账实对账。

> 画面：2014 Mt.Gox密钥层、对账是 · 多年后部分赔付每日账实对账

**[12.5]** 规律是，用户会不会买单，取决于账实是否一致，以及有没有储备兜底。

> 画面：规律：账和实对不对得上、有没有储备兜底，决定了谁来买单。

## 场景 13：账本隔离与储备金证明

**画面标题**：资产 ≥ 用户余额总和，怎么证明？（逐步动画）

**[13.0]** 为什么账本隔离和储备金证明这么重要？来看一组示例数字。

**[13.1]** 用户在账本里的余额加起来，示例是100亿美元。这是平台对用户的负债。

**[13.2]** 储备金证明要证明，平台持有的资产大于等于用户余额总和。示例里平台持有105亿，覆盖率105%。

**[13.3]** 如果客户资产被挪用，账面上用户还有100亿，平台实际只剩60亿。覆盖率60%，挤兑一来就兑付不了。

**[13.4]** 储备金证明用默克尔树，让每个用户都能验证自己的余额被计入了总负债。FTX 事件后，币安等交易所开始定期发布。

> 画面：默克尔树：每个用户可验证自己的余额被计入总负债。FTX 事件后，币安等交易所定期发布。

**[13.5]** 但它有局限。它只证明某一时刻，平台可以在快照前临时借入资产。它也不能证明平台没有隐藏负债。所以完整的保障还需要独立审计。

> 画面：局限：只证明某一时刻；快照前可临时借入资产；不能证明没有隐藏负债 → 还需要独立审计

**[13.6]** 客户资产隔离补上另一半。平台自有资金亏了，也不会传导到客户资产。

> 画面：客户资产隔离：平台自有资金亏损，不传导到客户资产

## 场景 14：边界、小结与系列结语

**画面标题**：四个容易忽略的边界（逐步动画）

**[14.0]** 最后看四个容易忽略的边界。第一，高可用不能替代正确性。重放逻辑有 bug，切换再快，订单簿也是错的。
