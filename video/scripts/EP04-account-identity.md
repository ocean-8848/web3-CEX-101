**画面标题**：账户与身份：谁在动这笔钱

**[1.0]** 大家好，欢迎回到交易所系统技术讲解。这一集我们讲账户与身份。先问一个问题。在交易所里，账户被盗意味着什么？

**[1.1]** 答案很直接。账户对应资产，账户被盗就是钱被盗。所以交易所的账户系统，比普通网站多了好几层锁。

## 场景 2：认证与授权

**画面标题**：两个问题：你是谁，你能做什么

**[2.0]** 开始之前，先分清两个词。认证，回答你是谁。授权，回答你能做什么。

**[2.1]** 这两件事要分开检查。比如一个只读 API Key，签名完全正确，认证通过了。但它仍然不能下单，因为没有这个授权。

> 画面：授权 Authorization确认“你能做什么”：只读 Key 验签通过，仍不能下单

**[2.2]** 本集按这条路线走。先讲登录、2FA 和设备指纹。再讲 API 签名和 KYC，最后是反钓鱼码和白名单。

> 画面：01登录与会话 02TOTP 2FA 03设备指纹 04API 签名与防重放 05KYC 分级与状态机 06反钓鱼码与白名单

**[2.3]** 打个比方，账户像银行保险箱。密码是大门钥匙，2FA 是门禁卡，白名单规定东西只能寄到固定地址。但比喻有个不成立的地方。交易所的锁都是校验逻辑，可以被绕过，所以要叠很多层。

> 画面：🔐 比喻：保险箱。密码 = 大门钥匙，2FA = 门禁卡，白名单 = 只能寄到固定地址。但每把“锁”其实是一段校验逻辑，可以被绕过。

## 场景 3：注册与登录

**画面标题**：密码只存慢哈希，登录要过多道检查

**[3.0]** 先看注册。用户提交邮箱或手机号，用验证码确认，再设置密码。业界通常只保存密码的慢哈希，并且加盐。例如 Argon2 或 bcrypt。

**[3.1]** 绝不能存明文，也不能用 MD5 这类快哈希。快哈希算得太快，数据库一旦泄露，很快就被暴力破解。

> 画面：✗ 快哈希 / 明文MD5 · SHA-256 · 明文计算成本太低，泄露后可被快速爆破

**[3.2]** 再看登录。系统先校验密码哈希，然后检查设备指纹和登录 IP。如果设备或地点异常，就要求二次验证。

> 画面：提交密码 校验哈希 设备与 IP 异常？二次验证 输入 2FA 签发会话

**[3.3]** 开启了 2FA 的用户，还要输入动态验证码。全部通过以后，系统才签发会话凭证。

> 画面：输入 2FA ｜ 签发会话

## 场景 4：会话令牌

**画面标题**：会话凭证：可吊销 vs 免查库

**[4.0]** 登录以后，系统给浏览器一个会话凭证。之后的请求带上它，就不用再输密码。凭证常见有两种形态。

**[4.1]** 第一种是不透明令牌，一个随机字符串，服务端查库才知道它属于谁。好处是能立即吊销，代价是每次都要查存储。

> 画面：不透明令牌随机字符串，服务端查库得知归属可立即吊销每次都查存储

**[4.2]** 第二种是 JWT，一段带签名的 JSON。服务端验签就能读出用户 ID，很快。缺点是签发以后，很难提前作废。

> 画面：JWT带签名的 JSON，验签即读出用户 ID不查库，快签发后难作废

**[4.3]** 业界通常组合使用。访问令牌有效期短，示例是 15 分钟。刷新令牌存在服务端，改密码或退出所有设备时，全部吊销。

> 画面：访问令牌 示例 15 分钟有效期短，泄露窗口小 刷新令牌 服务端可吊销改密码、退出所有设备 → 全部吊销

**[4.4]** 还有一个常见误区。JWT 的内容只是 Base64 编码，不是加密。任何人都能解码看到，所以不要在里面放敏感信息。

> 画面：JWT 只是 Base64 编码，不是加密：任何人都能解码读到内容。

## 场景 5：TOTP 双因素认证

**画面标题**：TOTP：密钥只传一次，之后各算各的（逐步动画）

**[5.0]** 现在看 2FA。它在密码之外，再验证一个你拥有的东西，也就是验证器。最常见的是 TOTP。绑定时，服务端生成随机密钥，做成二维码，用户扫码保存。

> 画面：⬅ Secret 仅在绑定时经二维码传输一次 ➡

**[5.1]** 之后双方各自计算。来算一个示例。当前时间是 1700000017 秒。除以 30 向下取整，得到 56666667。这就是时间窗编号，每 30 秒加 1。

**[5.2]** 双方用 HMAC-SHA1 处理密钥和窗口编号，截取 6 位数字。示例是 492039。输入相同，结果就相同。

**[5.3]** 注意，网络上只传这 6 位数，密钥从不传输。服务端通常还允许前后各 1 个时间窗，容忍手机时钟误差。

> 画面：网络上只传 6 位数：492039 服务端比对前后各 1 个时间窗 T−1TT+1

**[5.4]** TOTP 也有弱点。数据库泄露，密钥也跟着泄露，所以要加密存储。短信验证码更弱，攻击者可以补办你的手机卡截获短信。这叫 SIM 卡劫持。

> 画面：库泄露 = Secret 泄露 → Secret 要加密存储短信验证码更弱：SIM 卡劫持可截获

## 场景 6：设备指纹

**画面标题**：把设备特征组合成一个标识

**[6.0]** 登录流程里提到了设备指纹。它是把浏览器或 App 的一组特征，组合成一个标识。比如操作系统、浏览器版本、分辨率、时区、语言和字体列表。

**[6.1]** 第一个用途，识别新设备。新设备登录时，系统要求二次验证，并给用户发通知。

> 画面：① 识别新设备新设备登录 → 二次验证 + 通知

**[6.2]** 第二，管理已授权设备，用户可以删掉陌生设备。第三，给风控提供信号。一台设备登录大量账户，可能是批量注册。

> 画面：② 已授权设备用户可删除陌生设备 ｜ ③ 风控信号一台设备登录大量账户 → 批量注册？

**[6.3]** 但要注意，设备指纹可以被伪造。它只是风险信号之一，不能单独作为放行的依据。

> 画面：设备指纹可以伪造：只是风险信号之一，不能单独作为放行依据。

## 场景 7：API Key 与 HMAC 签名

**画面标题**：签名 = HMAC-SHA256(secretKey, 参数串)（逐步动画）

**[7.0]** 程序化交易要用 API Key。它分两部分。API Key 是公开标识，随请求明文发送。Secret Key 是签名密钥，永远不发送。

> 画面：Secret Key只在本地签名，永不发送NhqPtmdSJYdKjVHj… ｜ API Key公开标识，放在请求头X-MBX-APIKEY: vmPUZE6m…

**[7.1]** 来看币安现货接口怎么签名。客户端先把参数拼成一个字符串。末尾加上 timestamp 和 recvWindow，单位是毫秒。

> 画面：symbol=BTCUSDT&side=BUY&type=LIMIT&quantity=0.01&price=60000&timestamp…

**[7.2]** 然后用 Secret Key 对这个字符串做 HMAC-SHA256。得到的摘要作为 signature 参数，附在请求后面。

> 画面：signature 示例c8db5682…38bd6b71

**[7.3]** 请求头带着 API Key，参数里带着签名，Secret 不在网络上出现。币安还支持 RSA 和 Ed25519 密钥。它们是非对称签名，服务端不保存私钥。

> 画面：POST /api/v3/orderHeader：API Key ✓ 参数：…&signature ✓ Secret：✗ 不在请求里 网关：…

**[7.4]** 网关按 API Key 查到 Secret，重算签名，再和请求里的比较。比较要用常量时间算法，否则攻击者能从响应耗时里逐位猜签名。

> 画面：网关：按 Key 查 Secret → 重算 → 常量时间比较

**[7.5]** 如果有人在路上把数量从 0.01 改成 10 呢？参数串变了，重算的签名对不上。没有 Secret，攻击者也算不出新签名。网关直接拒绝。

## 场景 8：timestamp 与 recvWindow 防重放

**画面标题**：原样重发的请求，签名照样正确（逐步动画）

**[8.0]** 签名能防篡改，但防不了一件事。攻击者截获完整请求，原样再发一遍，签名完全正确。这就是重放攻击。

**[8.1]** 币安规定，服务器时间减 timestamp，不能超过 recvWindow。timestamp 也不能比服务器快 1 秒以上。recvWindow 默认 5000 毫秒，最大 60000。

> 画面：接受条件：服务器时间 − timestamp ≤ recvWindow 且 timestamp < 服务器时间 + 1s

**[8.2]** 来算一个示例。把 timestamp 记为 T。服务器在 T 减 1 秒到 T 加 5 秒之间收到，都接受。正常请求 T 加 0.2 秒到达，通过。

**[8.3]** 攻击者截获了请求，在 T 加 8 秒重放。服务器一算，差了 8000 毫秒，超过 5000，直接拒绝。

**[8.4]** 但如果攻击者在 T 加 3 秒就重放呢？时间窗没过，签名也对。所以 recvWindow 只能缩短重放窗口。下单接口通常再用 newClientOrderId 去重，同一个只接受一次。

**[8.5]** 再看两个边界。recvWindow 设成 60000，重放窗口就拉长到 1 分钟。所以网络稳定时用小值。另外，客户端时钟偏慢，正常请求也会被拒，要先调服务器时间接口校准。

## 场景 9：API Key 权限

**画面标题**：验签通过之后：这个 Key 能做什么

**[9.0]** 签名只解决认证。接下来是授权。币安的 API Key 有权限开关，读取、现货、合约和提币分开控制。

> 画面：权限开关读取 · 现货交易 · 合约交易 · 提币，分开控制

**[9.1]** 第二个配置是 IP 白名单，只允许指定 IP 使用这个 Key。根据币安公开资料，开启提币权限时，必须绑定 IP 白名单。

> 画面：IP 白名单只允许指定 IP 使用；开启提币权限时必须绑定

**[9.2]** 第三，Secret 只在创建时展示一次，遗失只能重建。提币权限风险极高，必须开时，同时绑定 IP 白名单和提币白名单。

> 画面：删除与重建Secret 只在创建时展示一次，遗失只能重建 ｜ ⚠ 提币权限风险极高：必须开时，同时绑定 IP 白名单 + 提币白名单。

**[9.3]** 打个比方。API Key 像支票账号，Secret 像签名笔迹。timestamp 像支票日期，过期就退回。但比喻不完全成立。有效期内，同一张支票仍可能兑现两次，所以要订单号去重。

> 画面：🧾 比喻：API Key = 支票账号，Secret = 签名笔迹，timestamp = 支票日期。不成立处：有效期内，同一张“支票”仍…

## 场景 10：KYC 分级

**画面标题**：认证越充分，功能越多，额度越高

**[10.0]** 现在换到监管视角。监管要知道用户是谁，要阻止洗钱。这就是 KYC，了解你的客户。它是反洗钱合规的基础。

> 画面：KYC = Know Your Customer，了解你的客户 · 反洗钱 AML 合规的基础 · 另有制裁名单筛查

**[10.1]** KYC 的思路是分级。认证越充分，可用功能越多，额度越高。根据币安公开资料，未认证用户功能受限。自 2021 年起，新用户要完成认证，才能交易和充提。

> 画面：未认证邮箱或手机号功能受限；自 2021 年起须认证才能交易和充提

**[10.2]** 已认证需要个人信息、身份证件和人脸识别，可以充值、交易和提币。高级认证再加一份地址证明，法币额度更高。

> 画面：已认证个人信息 + 身份证件 + 人脸识别加密货币充值、交易、提币 ｜ 高级认证再加地址证明更高的法币额度

**[10.3]** 企业认证面向机构，要提交公司注册文件，以及股东和董事信息。注意，具体要求按国家和地区变化，以官网为准。

> 画面：企业认证公司注册文件、股东与董事信息机构账户功能

## 场景 11：KYC 状态机

**画面标题**：KYC 是一个会回退的状态机（逐步动画）

**[11.0]** KYC 的处理流程是一个状态机。这张图是业界通用做法的抽象，不是币安内部的原样复刻。先看最顺的路径。注册完成是未开始，用户提交资料，进入自动审核。

**[11.1]** 自动审核会做证件识别、活体检测和名单筛查。证件和人脸比对通过，名单也没有命中，就直接批准。

**[11.2]** 如果置信度低，或者名单疑似命中，就转人工审核。人工可以批准，可以要求补充资料，也可以拒绝。用户补充资料以后，重新回到已提交。

**[11.3]** 命中制裁名单通常直接拒绝，还可能触发账户冻结。被拒绝的用户，可以在有限次数内重新提交。

**[11.4]** 最后注意，批准不是终点。证件过期或定期复审到期，状态会变成过期。用户要更新资料，重新提交。

## 场景 12：攻击路径与多层防护

**画面标题**：攻击者要连闯六道关（逐步动画）

**[12.0]** 把这些锁串起来，看一次完整攻击。第一步通常是钓鱼邮件。反钓鱼码就是用来识破它的。用户自己设一段暗号，币安官方邮件都会带上。

> 画面：✅ 官方邮件您的反钓鱼码：K7BLUEFOX（示例）您正在从新设备登录…… ❌ 钓鱼邮件没有反钓鱼码账户异常，请立即点击链接验证……

**[12.1]** 钓鱼者不知道暗号，邮件里就没有。假设用户没注意，在钓鱼网站输入了密码。攻击者拿到了第一把钥匙。

**[12.2]** 下一道锁是 2FA。没有开 2FA，攻击者直接登录成功。开了 2FA，攻击者还得拿到动态码。新设备登录还会触发二次验证，并通知用户。

> 画面：未开 2FA → 拿到密码即登录已开 2FA → 还要动态码新设备 → 二次验证 + 通知用户

**[12.3]** 假设这些也被突破了。下一道锁是提币白名单，只能向预先登记的地址提币。新增地址需要 2FA 和邮件确认。业界常见还有冷静期，示例是 24 小时内新地址不能提币。

> 画面：提币到攻击者地址：✗ 不在白名单新增地址：2FA + 邮件确认 → 冷静期 24 小时 示例

**[12.4]** 冷静期的价值是争取时间。用户收到告警，可以自助冻结账户。风控看到新设备、新地址加大额，也会转人工审核。

> 画面：冷静期 = 争取时间用户收到告警 → 自助冻结账户风控：新设备 + 新地址 + 大额 → 人工审核

**[12.5]** 这套防线也有局限。如果用户的邮箱也被攻破，邮件确认这一层就失效了。每一层都可能被绕过，所以要靠多层叠加，抬高攻击成本。

> 画面：局限：邮箱也被攻破时，邮件确认这一层失效。每层都可能被绕过 → 靠多层叠加抬高攻击成本。

## 场景 13：常见误区

**画面标题**：三个常见误区

**[13.0]** 最后看几个常见误区。第一个，开了 2FA 就不怕钓鱼。其实不然。用户在钓鱼网站上输入验证码，攻击者可以实时转发给真网站。

> 画面：✗ 开了 2FA 就不怕钓鱼钓鱼网站可实时转发验证码 → 通行密钥 / 硬件密钥绑定域名，防得住

**[13.1]** 能防住这一类攻击的，是通行密钥和硬件安全密钥。它们和域名绑定，假域名拿不到有效签名。根据币安公开资料，这两种方式币安都支持。

**[13.2]** 第二个误区，以为 KYC 能证明谁在操作账户。KYC 只证明提交资料的人是谁。账户被出售或出借，KYC 发现不了。

> 画面：✗ KYC 证明了谁在操作账户只证明提交资料的人是谁；账户被出售、出借时发现不了

**[13.3]** 第三个误区，觉得 Secret 保管好就够了。现实中常见的泄露，恰恰是把 Secret 写进了公开代码库。防护要靠最小权限、IP 白名单，以及关闭提币权限。

> 画面：✗ 不泄露 Secret 就万事大吉最常见的泄露：Secret 写进公开代码库 → 最小权限 + IP 白名单 + 关提币
